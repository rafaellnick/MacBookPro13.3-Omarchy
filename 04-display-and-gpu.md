# 04 — Display and GPU

This machine has **two GPUs and one internal panel**, with the panel wired to
whichever GPU the `apple_gmux` mux selects. That single fact explains most of
the surprises in this module.

- Intel HD 530 iGPU — `0000:00:02.0`
- AMD Radeon Pro 455 — `0000:01:00.0`, and **all external DisplayPort outputs
  hang off it**

Current state: mux on the **AMD GPU**, panel on `card1-eDP-1` at 2880x1800,
i915 runtime-suspended.

---

## 4.1 External display stuck at 60 Hz

Samsung Odyssey G30B on `DP-3`, via a **USB-C → HDMI adapter**.

### The first diagnosis was wrong

Originally read as bogus EDID caps that should be overridden by forcing 4 lanes.
That was backwards, and the forcing is what caused the damage.

### Actual cause

The EDID is fine — it carries `1920x1080@120` (297 MHz) and `@144` (351 MHz),
and the range block says 48–144 Hz.

The **adapter latches its advertised DP caps down after a failed link training**.
A fresh plug offers 2 lanes at HBR2 (~8.6 Gbps usable). Overshoot the bandwidth
once and it drops to 1 lane and **stays there until physically replugged** — no
amount of `trigger_hotplug`, resume or reboot recovers it. amdgpu believes the
advertised caps, so at 1 lane everything above 1080p60 is pruned.

Forcing `4 0x14` trained four lanes against a sink that only ever had two → link
failed under load → adapter demoted itself.

> **Do not force more lanes than the sink reports.**

### Bandwidth at 2 lanes / HBR2 (8.64 Gbps usable)

| Mode | Needs | Fits |
|---|---|---|
| 1920x1080@60 | 3.56 Gbps | yes — even at 1 lane |
| 1920x1080@120 | 7.13 Gbps | yes, comfortably |
| 1920x1080@144 | 8.42 Gbps | 2.5 % margin — **does not train**, and that failure is what latches the adapter |

144 Hz is out of reach for a second reason too: the EDID's HDMI block caps TMDS
at 340 MHz and the 144 Hz timing needs 351 MHz. **Ask for 120, never 144.**

### Fix — ⚠️ REVERTED, NOT CURRENTLY APPLIED

**Status 2026-09-07: all of the following was removed at the user's request**
("revert everything that was made to fix the 120 Hz output"). None of these
files exists on the machine now:

- `/usr/local/bin/dp3-link-hbr2` — absent
- `/etc/systemd/system/dp3-link-hbr2.service` — absent
- `/etc/udev/rules.d/99-dp3-link-hbr2.rules` — absent

The external monitor therefore runs at whatever the adapter negotiates, with no
intervention. The analysis below is retained because it is correct and would be
the basis of any future attempt — but **it describes a fix that is not in
place.**

- `/usr/local/bin/dp3-link-hbr2` — reads the sink's *reported* lane count and
  pins the preferred link setting to `2 0x14` for two lanes, `1 0x14` for one,
  then triggers a hotplug so mode validation reruns. No-ops when the preference
  already matches, since the hotplug is what re-runs the script via udev.
- `/etc/systemd/system/dp3-link-hbr2.service` — oneshot, wanted by
  `graphical.target` and `suspend.target`.
- `/etc/udev/rules.d/99-dp3-link-hbr2.rules` — re-applies on any DRM hotplug.

The debugfs setting is runtime-only — it resets on every replug, resume and
reboot, which is why all three triggers exist.

**Recovering 120 Hz requires physically unplugging and replugging the adapter.**

### ⚠️ The Hyprland monitor rule lives in two places and they disagree

`hyprland-gui.lua` is generated by HyprMod and is `require`d at line 36 of
`hyprland.lua` — *after* `hypr.monitors` at line 19 — so it wins. It hardcodes
`1920x1080@60.00Hz`, which means the dynamic selection in `monitors.lua` never
takes effect.

Both say 60 Hz today so behaviour matches, but once a replug restores two lanes
the generated file will still pin 60. Either clear the DP-3 block from
`hyprland-gui.lua` or regenerate it after the link is back at 120.

`hyprctl keyword monitor` does **not** work on this Lua-parsed config — use
`hyprctl eval 'hl.monitor({ ... })'` to test a rule live.

**Both the old force-4-lanes version and its replacement are gone.** The only
display-related leftover is a `DP-3` block in `~/.config/hypr/hyprland-gui.lua`
(line 23), which is harmless with no monitor attached.

## 4.2 Lid close did not suspend when docked

`systemd-logind` treats "an external display is connected" as **docked**, and
`HandleLidSwitchDocked` defaults to `ignore`. logind logged `Lid closed.` and
deliberately did nothing, while Hyprland reacted to `eDP-1` going away — which
looked like a failed suspend.

**Fix:** `/etc/systemd/logind.conf.d/30-lid-suspend-when-docked.conf` sets
`HandleLidSwitchDocked=suspend`. Set it back to `ignore` for clamshell mode.

## 4.3 The GPU mux, and why the panel selection matters

`apple_gmux` switches the panel's data lanes **and its AUX channel** together.
Selection is made by the EFI variable `gpu-power-prefs` and only takes effect at
power-on.

`/usr/local/sbin/gpu-mode` (`igpu` / `dgpu` / `status`) writes it;
`/usr/local/sbin/gpu-switch` is the lower-level writer.

**Current state: NVRAM was reset, so the firmware default (AMD) applies.**
`gpu-mode status` reports `EFI selection : unknown (unreadable)` for that reason
— the variable is absent, not broken.

Running on the iGPU is possible and was demonstrated working, but it is **not
recommended** — external DisplayPort outputs stop working entirely, and it
measured *worse* for power. See [10-dead-ends.md](10-dead-ends.md) §10.2 and
[06-power-and-battery.md](06-power-and-battery.md).

> **Recovery if a mux change ever leaves a black screen:** hold
> **⌘ + ⌥ + P + R** at the boot chime through two more chimes. That resets NVRAM
> and returns the mux to the AMD GPU. No rescue USB needed.
